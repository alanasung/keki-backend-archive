# Contributing

This is a summary of the workflow and conventions for working in this
repository. [`AGENTS.md`](AGENTS.md) is the authoritative conventions
document — if anything here and `AGENTS.md` disagree, `AGENTS.md` wins, and
this file should be corrected to match it.

## The four verify commands

Every workspace package (`apps/*`, `packages/*`, `functions/*`) defines all
four of these scripts in its `package.json`:

- `typecheck`
- `lint`
- `test`
- `build`

Run across the whole workspace from the repo root:

```sh
pnpm -r typecheck
pnpm -r lint
pnpm -r test
pnpm -r build
```

This is the same sequence, in the same order, that `.github/workflows/ci.yml`
and `pipeline.config.json`'s `verify` block run. All four must exit
successfully before a change is done — a bare `pnpm -r` invocation fails
outright on any package missing one of the four scripts, so a new package
must define all four from the start. A package with nothing to build yet
still defines a `build` script (a `tsc --noEmit` compile gate, not an emit
step — see "Source-export convention" below) and a `test` script that runs
its own, possibly empty, Vitest project. Don't use `--if-present` to work
around a missing script.

See [`docs/testing.md`](docs/testing.md) for what each test layer covers and
its prerequisites.

## Source-export convention

Internal `packages/*` libraries are consumed as source, not as a built
artifact. Each package's `main`, `types`, and `exports` point at
`./src/index.ts` rather than a built `dist/`:

```json
{
  "main": "./src/index.ts",
  "types": "./src/index.ts",
  "exports": { ".": "./src/index.ts" }
}
```

Next.js transpiles the source directly via `transpilePackages`, and Lambda
handlers in `functions/` bundle it with esbuild at deploy time. A library's
`build` script is therefore a compile gate (`tsc --noEmit -p tsconfig.json`)
that catches type errors, not an emit step — don't invent a per-package emit
pipeline or point `main`/`types` at a `dist/` directory.

## Module boundaries

- `packages/*-core` are plain TypeScript libraries. They must not import
  from `apps/web`, and must not depend on Next.js, React, or any AWS SDK
  surface beyond what they genuinely need. This is enforced two ways: an
  ESLint `import/no-restricted-paths` rule (`eslint.config.mjs`) blocks any
  `packages/*-core` file from importing `apps/**`, and each core package has
  a `package-boundaries.test.ts` asserting its `package.json` lists no other
  `@keki/*-core` package as a dependency — no core package depends on
  another core package.
- Domain packages are imported directly by Next.js Server Actions and by
  Lambda handlers in `functions/`. Don't introduce an internal HTTP hop
  between the app and the core.
- Don't create a Lambda per package. `functions/` holds exactly the four
  asynchronous workers; deployment boundaries are chosen per workload, not
  per module.
- `packages/contracts` holds shared types and schemas. When a type crosses a
  package boundary, it belongs there, not duplicated at both ends.

See [`docs/architecture.md`](docs/architecture.md) for why the boundaries are
drawn this way.

## Migrations

Migrations are generated by drizzle-kit, not hand-written:

```sh
pnpm --filter @keki/database db:generate
```

The generated SQL is hand-edited in exactly two places, both called out
where they occur:

1. `CREATE EXTENSION IF NOT EXISTS citext` is added as the first statement
   of the initial migration — drizzle-kit cannot infer that the `citext`
   custom type (`packages/database/src/schema/people.ts`) requires a
   Postgres extension.
2. The `play_pass_ledger` append-only trigger (`BEFORE UPDATE OR DELETE ...
   RAISE EXCEPTION`) is appended to the migration that creates that table —
   drizzle-kit has no schema-level way to express "no updates or deletes,
   ever" (`packages/database/src/schema/passes.ts`).

Any other divergence between the schema and the generated SQL is a bug, not
a hand-edit — regenerate instead of patching.
